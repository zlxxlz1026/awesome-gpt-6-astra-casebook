本指南基于已收录的作者资料进行需求拆解，项目编辑建议与作者公开提示词明确区分。

## 三个案例，三种提示词重点

| 案例 | 资料中的重点 | 可以借鉴什么 | 不能据此推断什么 |
| --- | --- | --- | --- |
| [Komorebi：林隙河流](../gallery.zh-CN.md#komorebi-river-run) | 短提示词同时写出皮划艇、左右划桨、躲避障碍和美术方向 | 先写玩家反复执行的动作，再定义画面风格 | 作者对美术和音乐的肯定不代表水体模拟已完善；作者也指出湍流不足 |
| [单文件峡谷驾驶](../gallery.zh-CN.md#single-file-canyon-racer) | 明确 3D 驾驶与单个 HTML 文件 | 把交付格式写成可检查条件 | 单文件不自动意味着离线可用；作者记录过一次打包修复，资料没有试玩链接 |
| [Little Acre 袖珍世界](../gallery.zh-CN.md#little-acre-world-builder) | 宽泛目标让模型决定建造、驾驶、昼夜与导出功能 | 当允许探索时，宽目标可用来征集方案 | 同一句提示词不保证生成同一组功能；资料记录了额度消耗与卡顿反馈 |

## 我们建议的第一版范围

从 Komorebi 的左右操作结构出发，把第一版限定为一条路线、两种输入、一个碰撞规则和一个重新开始按钮。先验证这个循环，再添加声音、装饰和更多关卡。对于 Little Acre 这类开放目标，先列出候选功能并选择一个闭环，例如“放置一个物体—保存—重新打开后恢复”，避免把创意清单直接当成验收要求。

若目标是汽车足球等复杂物理游戏，可以阅读[汽车足球案例](../gallery.zh-CN.md#rocket-league-threejs)：其资料把车辆、球体、场地、镜头和比赛循环一起写入需求。初次尝试可先缩小为车辆与单个球体的交互；这属于本项目建议，不是作者原始方案或经过验证的捷径。

## 小型浏览器游戏需求清单

以正文引用的作者公开提示词为参考，再为自己的项目明确以下要求：

- 核心循环：玩家反复执行的动作、障碍或对手、成功条件和失败条件。
- 操作方式：支持键盘、鼠标、触屏还是手柄。
- 内容范围：先完成一条完整路线或一个关卡，再扩展更多内容。
- 交付形式：源码、启动方式、依赖清单和联网策略。
- 原创性：使用原创素材与机制，不照搬受保护角色或关卡。
- 可调参数：速度、难度、碰撞范围和计分集中管理并清晰命名。
- 验收行为：开始、输入、碰撞、暂停、继续、结算和重新开始。

## 验收清单

| 检查 | 通过条件 | 需要记录 |
| --- | --- | --- |
| 打开交付物 | 按说明启动后出现可操作场景 | 启动方式、浏览器版本、日志 |
| 输入 | 左右输入产生对应移动，不会卡在按下状态 | 键盘/触屏是否实际测试 |
| 碰撞与结算 | 碰撞按规则触发，得分与结果一致 | 一次正常流程和一次边界情况 |
| 暂停与继续 | 暂停期间游戏状态不推进，恢复后继续 | 前后状态截图或录屏 |
| 重新开始 | 清除上一局状态，并可以再次完整游玩 | 至少两局的操作记录 |
| 打包 | 从干净目录按说明运行；若声称离线，断网后也可启动 | 外部请求、缺失资源、实际联网状态 |

视频录屏只能证明可见片段。不要用它代替输入、重开或离线检查；完整提示词也不能代替缺失的代码、素材与环境。

## 记录迭代，而不是只保留最好的一帧

保存初始提示词、每轮修改、实际耗时、模型标签与设置、测试环境以及失败原因。费用只记录有账单或用量依据的数据；作者的额度百分比不能换算成你的固定成本。使用[复现记录规范](../reproduction/README.md)，区分“试玩现成作品”和“重新生成并复现”。
